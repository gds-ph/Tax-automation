## PAD incident record and recovery rules

- **20 October, 1601EQ preparation:** parent reported a child-flow timeout before
  output files existed. The stopped attempt was abandoned using the service and
  retried; the replacement reached `AWAITING_SUBMISSION_APPROVAL`.
- **20 October, clean dispatcher exit:** logs reported Success rather than a
  runtime exception after a completed 2550Q submission. The completed submission
  was not replayed. Restarting the parent allowed a subsequent preparation to
  complete. The specific clean-exit branch was not established.
- **21 October, 2550Q preparation:** XML and page 1 existed, but page 2's filename
  stayed blank and the child timed out. The repaired flow retains 116 actions,
  21 inputs and 3 outputs. Its six save-dialog references were changed and verified
  by copying the installed actions back out.
- The parent editor had been open since 18 October, used approximately one CPU
  core and took 10–15 seconds between simple statements. Stop/close became
  unresponsive. Runtime termination was limited to the identified dispatcher and
  its children after checking an unstarted `ReadyToRun` claim, no eBIR process and
  no active submission. Normal processing was resumed from the PAD console.
- The first retry correctly refused to overwrite the interrupted XML. That XML
  was preserved in the worker recovery archive; a version-checked, audited
  operator recovery requeued preparation. The final attempt produced both page
  PDFs and the merged PDF, and the server recorded success and approval-pending
  status. The dispatcher automatically started the next job.

Do not delete journals or blindly rerun a submission to clear a stop. Check
server state, local phase, output artifacts and evidence first. A publication
failure after submission calls for publishing existing evidence, not submitting
again. See [preparation recovery](worker-preparation-recovery.md) and
[submission reporting recovery](stage2-reporting-recovery.md).

## What is and is not in Git

This push contains application code, worker scripts, tests, operating guides and
the PAD export inventory. Installed desktop flows are separate from Django and
are not installed by pulling this repository.

Raw PAD exports in the sibling `outputs/` directory include captured UI images
and can contain taxpayer information. They remain local; the inventory records
filenames, hashes, changes and verification. Credentials, journals, databases,
client source workbooks, return XML/PDFs and runtime logs are also excluded.
Retain these separately in restricted backups if disaster recovery is required.
